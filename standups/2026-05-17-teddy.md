## WikiGenerator — Section wiki ordering fix

**Root cause:** Section wiki generation ran *before* Pass 1. On Ministral 3B Q4, the model generates ~350 tokens of truncated JSON per attempt (3 attempts × Evening = 1050 tokens wasted). Device thermals rose to `.serious` before Pass 1 even started, causing Pass 1 to return 0 sections and Pass 2 to get an empty response → timeout.

**Fix:** Moved section wiki generation to *after* `store.save(article:sources:)`. The main article (Pass 1 + Pass 2) is now always saved first. Section wikis run as optional supplements post-save with a fresh thermal check. If they fail (common on Ministral 3B), the user gets the main article regardless.

**Files changed:** `PrivateCore/Services/WikiGenerator.swift`
- Removed section wiki loop and `sectionWikiSummaryLines` injection from pre-Pass-1 block
- Added post-save section wiki loop with per-iteration `.nominal || .fair` thermal gate
- Simplified Pass 2 `sectionHint` to `"Overview, Timeline, Events, Captures"` (no longer references section links that don't exist yet at generation time)

## WikiGenerator — Partial JSON recovery

**Problem:** Ministral 3B stops generating mid-JSON (~350 tokens). All 3 attempts produce truncated JSON → `parseWikiJSON` returns nil → `generationFailed` thrown → user sees timeout. Pass 2 attempt 1 had a valid 1663-char response with a complete `lead` field that was being discarded.

**Fix:** Added `extractLeadFromPartialJSON(_:)` — regex extracts `"lead": "..."` from the best (longest) partial response. If all attempts fail full JSON parse, a minimal article with just the lead and empty sections is returned instead of throwing. User sees the opening paragraph + skeleton sections instead of an error.
